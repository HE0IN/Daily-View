# 09. AI 정리 · RuleBook 계획

> 작성: 2026-07-09 · 상태: **설계 합의 완료, 구현 전**
> 카테고리 자동화 + Temp 정리 + 규칙 지식 페이지(RuleBook) 도입 계획.

## 9.1 배경 (문제 3가지)

1. **카테고리가 사실상 죽어있음** — 수동 입력이라 귀찮아서 안 넣고,
   애초에 "어떻게 나눌지" 체계를 정한 적도 없음.
2. **Temp가 뒤죽박죽 창고가 됨** — '정립된 규칙' / '룰이 애매한 것' /
   '확인해봐야 하는 것'이 구분 없이 쌓여 있음.
3. **기준 지식이 파편화** — 어떤 기능이 어떤 데이터·수치·기준으로
   동작하는지가 Temp 여기저기에 흩어져 있어 찾을 수 없음.

세 문제의 공통 원인: **Temp 에 '성격'을 구분하는 축이 없다.**
축이 없으니 창고가 되고, 확정 규칙만 골라낼 수 없으니 규칙집도 못 만들고,
카테고리 축이 없으니 묶을 방법도 없다.

## 9.2 확정된 설계 결정

| # | 결정 | 내용 |
|---|------|------|
| D1 | 성격 라벨은 **3개** | 미분류(기본) / 🔍 확인필요 / ✅ 확정규칙. '논의필요'는 확인필요에 통합 — 확인필요 자체가 "모여서 논의하는 단계"(규칙 확정? 보류? 바로 개발?)이므로 따로 둘 이유 없음 |
| D2 | 라벨은 **항목 자체의 필드** | meta.json 에 저장. Temp 전용이 아니라 확인요청 시점부터 항목을 따라다님. dev(개발) 항목은 라벨 대상 아님 — 카테고리 제안만 받음 |
| D3 | RuleBook 은 **뷰(view), 이동 없음** | `kind=criteria & rule_status=확정규칙` 항목을 카테고리별로 노출. 항목은 계속 Temp 로 존재(폴더·ID·이미지·코멘트·이력 그대로). 라벨 되돌리면 RuleBook 에서 사라짐 |
| D4 | Temp 목록에서 확정규칙 **기본 숨김** | 양쪽 중복 노출 방지. 토글로 표시 가능. "정리 안 된 것만 Temp 에 남는" 효과 → 정리 진행도가 눈에 보임 |
| D5 | AI 는 **제안만**, 적용은 사람 | 제안 → 검토 → 일괄 적용 3단계. 승인 전에는 데이터가 절대 안 바뀜. 적용은 repository 함수 경유(건별 시스템 코멘트 + audit) |
| D6 | AI정리는 **별도 페이지** | Streamlit 은 백그라운드 작업이 없어 "등록 즉시 자동판단" 불가 → 판단 실행 + 제안 검토·승인의 '장소'가 필요. AI 제안 수신함 개념 |
| D7 | 판단 결과 **캐시** | 내용 해시 기준. 판단된 항목은 재호출 안 함. 내용 수정 시 해시가 바뀌어 자동으로 재판단 대상 |
| D8 | 카테고리 체계 제안은 **루프 설계** | 한 방 정답 불가(generic 트리 위험). 태깅→집계→초안→배정테스트→사람수정 반복 (9.6) |
| D9 | 내비 **5구역** | AI질문을 3구역에서 빼서 담당팀요청 아래 새 AI 구역으로. RuleBook 은 2구역(Temp 옆, 룰 파이프라인 종착지) |

## 9.3 내비게이션 (5구역)

```
[내작업 · 개발목록 · 신규등록]
[확인요청 · 확인요청목록 · Temp · RuleBook]      ← RuleBook 추가
[대시보드 · 통계 · 상세보기]
[개발사요청 · 담당팀요청]
[AI질문 · AI정리]                                ← 신설 AI 구역 (AI질문 이동)
```

## 9.4 데이터 모델 / 저장

- `Issue.rule_status: str = "unsorted"` — `"unsorted" | "needs_check" | "confirmed"`.
  pydantic 기본값이라 기존 meta.json 과 하위호환 (필드 없으면 미분류로 로드).
- 제안 캐시: `data/ai/suggestions.json` — 항목별
  `{item_id, content_hash, 제안(라벨/카테고리/한줄요약), 제안시각, 상태(대기/승인/무시)}`.
  기존 file_lock 패턴으로 보호.
- 카테고리 풀: 기존 구조 재사용 (승인된 트리로 갱신).

## 9.5 운영 흐름

```
확인요청 등록 (기존과 동일, 바뀌는 것 없음)
      │
      ▼
AI정리 페이지 열기 → 미판단 항목만 자동 LLM 판단 (15~20개 청크, 캐시)
      │
      ▼
제안(성격 라벨 + 카테고리 + 한줄요약) 검토 → 승인/수정 → 일괄 적용
      │
      ├ ✅ 확정규칙 → RuleBook 에 노출 (Temp 목록에선 기본 숨김)
      ├ 🔍 확인필요 → 논의 대기 버킷
      │     └ 논의 결과: 라벨→확정규칙 / 그대로 두기(나중에) / 기존 [개발요청] 버튼으로 개발 전환
      └ 개발 항목 → 카테고리만 배정
```

- 기존 Temp 물량: AI정리 페이지에서 **최초 1회 back-fill** (전량 판단 → 승인 스윕).
- 논의필요/확인필요 결과 처리는 전부 기존 기능(라벨 변경 · 개발요청 버튼)으로 — 새 메커니즘 없음.

## 9.6 카테고리 체계 제안 파이프라인 (D8)

```
① 태깅     : 항목 15~20개씩 → 각각 자유 주제 태그 2~3개 (LLM)
② 집계     : 태그 빈도 카운트 (코드, LLM 아님)
③ 트리 초안 : 상위 태그 + 기존 카테고리 풀(앵커) → 2단 트리 제안 (LLM)
④ 배정 테스트: 초안 트리로 전체 항목 배정 → "미배정 N건" 리포트
⑤ 사람 수정 : 트리 편집 → 미배정 줄어들 때까지 ③~④ 반복
```

- 핵심 검증은 ④: 좋은 체계 = 실제 항목이 다 들어가는 체계.
- 기존 입력된 카테고리가 있으면 앵커(예시)로 프롬프트에 포함해 도메인 톤 고정.
- 청크 방식이라 항목 수백 건이어도 컨텍스트 한계에 안 걸림.

## 9.8 기술 제약 / 노트

- Streamlit 백그라운드 작업 없음 → 판단은 페이지 상호작용 중 실행 (spinner + 청크 진행표시).
- LLM: 사내 gemma-4-31b (OpenAI 호환), `LLM_TIMEOUT=120s`.
  JSON 응답은 마크다운 펜스 제거 등 견고 파싱 필수 — 실패 청크는 스킵하고 리포트.
- LLM 이 파일을 직접 쓰는 경로는 없음 — 모든 적용은 승인 후 repository 함수 경유 (audit 기록).
- 청크당 15~20개 항목: 타임아웃·컨텍스트·JSON 안정성의 균형점.
